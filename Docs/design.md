# 設計書 (Design Document)

## 1. 基本設計 (Basic Design)

### 1.1 概要と目的
本機能は、保有・監視銘柄に対して「週足スイングトレード戦略」に基づいたテクニカル分析を自動実行し、売買シグナルを生成・提示することを目的とする。
ユーザーはフロントエンドの「Check Signal」ボタンを押下することで分析を開始し、結果（スコア、検出パターン、推奨アクション）を画面上で確認できる仕組みを提供する。

### 1.2 アーキテクチャ方針
- **Backend Driven**: 分析ロジックの中核は Python バックエンド (`python/watch/analyze.py`) に集約し、pandas 等を用いた数値解析を行う。
- **Async Processing**: 分析処理は計算負荷が高いため、APIリクエスト受付と分析実行を分離（または非同期化）し、UI の応答性（2秒以内）を維持する。
- **Database Persistence**: 分析結果は一時的な表示にとどめず、データベースに履歴として永続化し、検証可能な状態にする。

### 1.3 コンポーネント構成

| コンポーネント | 役割 | 関連ファイル/技術 |
| :--- | :--- | :--- |
| **Analysis Engine** | トレード戦略の実装（環境認識、パターン検出、スコアリング） | `python/watch/analyze.py` |
| **Database** | シグナル履歴、銘柄データの保存 | PostgreSQL / SQLite (SQLAlchemy) |
| **API Layer** | 分析リクエストの受付、結果データの提供 | FastAPI (想定) / `main.py` |
| **Frontend UI** | 分析トリガーボタン、結果一覧表示 | `index.html`, JavaScript |

## 2. 詳細設計 (Detailed Design)

### 2.1 トレード戦略ロジック (Analysis Logic)
`python/watch/analyze.py` の `main()` 関数をエントリーポイントとして、以下のパイプラインを実装する。

1.  **データ取得**: 登録されている全保有・監視銘柄の週足データを取得。
2.  **環境認識フィルター (Environment Filter)**:
    - **判定基準**: 40週移動平均線 (40MA)
    - **Long**: 終値 > 40MA かつ 40MAが上向き
    - **Short**: 終値 < 40MA かつ 40MAが下向き
3.  **パターン検出 (Pattern Detection)**:
    - **対象**: ダブルボトム、逆三尊、フラッグ、トライアングル等。
    - **補強**: 出来高の増加（20週平均比）を確認。
4.  **スコアリング (Scoring)**:
    - 加点方式: トレンド一致(+3)、パターン完成(+3)、出来高増(+2)、RSI確認(+1)、RR良(+1)。
    - **閾値**: 合計8点以上でエントリー候補とする。
5.  **リスク管理計算 (Risk Management)**:
    - **損切り**: エントリー時 ATR(14) × 1.5
    - **利確**: リスクリワード比 (RR) 1:2 以上
    - **ポジション**: 1トレードの最大損失を資金の 1% に制限

### 2.2 データベース設計 (Schema)
分析結果を保存する `signals` (仮称) テーブルを定義する。

| カラム名 | データ型 | 説明 |
| :--- | :--- | :--- |
| `id` | Integer | Primary Key |
| `symbol` | String | 銘柄コード |
| `analysis_date` | Date | 分析実行日 |
| `signal_type` | String | 'LONG', 'SHORT', 'NONE' |
| `score` | Integer | 算出されたトータルスコア |
| `detected_patterns` | JSON/String | 検出されたパターン名のリスト |
| `stop_loss` | Float | 計算された損切り価格 |
| `take_profit` | Float | 計算された利確目標価格 |
| `rationale` | Text | 判定根拠のサマリ |
| `created_at` | DateTime | レコード作成日時 |

### 2.3 API エンドポイント設計
- **`POST /api/analyze`**: 分析タスクの開始トリガー。
  - レスポンス: 処理受付メッセージ（202 Accepted）。
- **`GET /api/signals/latest`**: 最新の分析結果一覧を取得。
  - レスポンス: 銘柄ごとのスコア、シグナル、詳細情報のリスト。

### 2.4 フロントエンド UI 設計
`index.html` および関連スクリプトの改修。

- **Check Signal ボタン**:
  - クリックイベントで `POST /api/analyze` をコール。
  - 処理中はボタンを無効化し、ローディングインジケータを表示。
- **結果表示エリア**:
  - `GET /api/signals/latest` の結果をテーブルまたはカード形式で表示。
  - 高スコア銘柄を強調表示。
  - ツールチップ等で詳細（検出パターン、リスク計算値）を表示。

## 3. 非機能要件
- **パフォーマンス**:
  - ボタン押下時のレスポンスは2秒以内とする（重い処理はバックグラウンドへ）。
- **運用・コスト**:
  - Cloud Run 利用時は Always Free 枠内での運用を目指し、リソース消費を最適化する。
  - 開発・テスト時はローカル環境 (Intel MacBook Pro + Ubuntu) を優先利用する。
- **保守性**:
  - シグナル生成ロジックはモジュール化し、パラメータ調整（MAの期間変更など）やルールの追加が容易な構成とする。
